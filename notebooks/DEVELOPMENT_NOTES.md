# Notebooks

Thin Colab wrappers. All logic lives in the `shipdoc` package; a notebook only mounts Drive,
reads secrets, clones the repo at a pinned commit, installs, and shells out to `python -m shipdoc`.
`notebooks/01_spike.ipynb` is generated by `scripts/colab_build_notebook.py` (outputs cleared);

## 01_spike: run instructions

One-time, on GG's machine (Windows):

1. `uv run python scripts/make_colab_zips.py` writes `assignment.zip`, `ocr_cache.zip` and
   `ZIPS_SHA256.txt` to `SHIPDOC_RUNS_DIR` (`$SHIPDOC_RUNS_DIR`). `data.zip` is built separately.
2. Upload `data.zip`, `assignment.zip`, `ocr_cache.zip` to
   `MyDrive/shipdoc-extract/` in the **your-drive-account@example.com** Drive. Compare the SHA256 of
   each with `ZIPS_SHA256.txt` if in doubt.
3. In Colab: Secrets (key icon), enable Notebook access for each:
   - `GH_TOKEN` (required, read access to `example-owner/example-repo`)
   - `WANDB_API_KEY` (required while `USE_WANDB = True`)
   - `HF_TOKEN` (optional)
4. W&B: the `shipdoc-extract-debug` project must be **Private**. The public API may not expose
   project access; if so the notebook prints an `ACTION FOR GG` line with the settings URL. Create
   the project as Private first (or set the account's default project privacy to Private).

Each run:

1. Open the notebook from GitHub in Colab at the **PIN commit** (the `chore(notebooks): pin
   01_spike to <sha7>` commit; use the commit-SHA URL, not `main`), Runtime -> Change runtime
   type -> T4 GPU. The notebook clones `CODE_SHA`, the commit just before the PIN commit, which
   is hardcoded as `PINNED_SHA` in `scripts/colab_build_notebook.py` and in the first code cell
   (the notebook asserts `HEAD == PINNED_SHA` after checkout). The PIN commit differs from
   `CODE_SHA` only in the notebook files (`git diff --stat CODE_SHA PIN`), so the code that
   runs is exactly `CODE_SHA`. To run newer code, re-pin: edit `PINNED_SHA` in the builder,
   regenerate, commit. `splits/spike40.json` is the default doc list; use
   `splits/dev100.json` is used automatically for the top-2 run.
3. Runtime -> Run all.

What it does: mounts Drive and checks the three zips, clones the repo, unzips `data/` and
`assignment/` to `/content/shipdoc-extract/` and the OCR cache to `/content/ocr_cache` (verifying
`SHA256SUMS`), runs `uv sync --frozen --group vlm`, prints the GPU / torch / transformers /
bitsandbytes / xgrammar versions (asserts a `sm_75` kernel or PTX exists), then prints the
GPU-hour and compute-unit estimate (see below; read it before the run, interrupt if it is too
high), then runs the mandatory smoke gate (see below), then runs the six COMPACT configs in the order of `configs/spike_order.json` (cheapest estimated first; edit the
file and regenerate the notebook to reorder; a test fails if the file is not cheapest first by
the measured speeds in `configs/spike_speed.json`, in which case regenerate it from
`scripts/gpu_estimate.py`). Configs of a model that failed the smoke gate are not run. Each config is its own subprocess, so GPU memory is
freed between configs and a CUDA OOM in one does not stop the others.

### Compute-unit (CU) estimate

Printed before anything runs; there is no confirmation prompt (Run all must not block), so read it
and interrupt if it is too high. It lists per-config T4 hours, then a stage table (smoke, spike40,
the keyed-vs-compact A/B, the conditional dev100 top-2 at compact speed and at keyed speed, each
at its costliest config(s) as the worst case) with T4 hours and CU at **1.19 CU/h** (observed
by a third party, mccormickml.com, checked 2026-03-10) and **1.58 CU/h** (varlog.info, measured
2024-10-01). Google does not publish a T4 rate; both numbers are in `configs/spike_speed.json`
with their sources, and the real rate is whatever Colab shows. Each model load is charged
`model_load_s` = 120 s, which is an ESTIMATE, not a measurement. The notebook reads the runtime GPU
name from `nvidia-smi`; if it is not a T4 it prints a warning that the speeds and rates are T4
figures. Colab exposes no programmatic CU balance, so the notebook prints "check Runtime -> Manage
sessions / Resources for your balance" instead of inventing one.

### Smoke gate (mandatory)

The fixes under test are unverified on a GPU (grammar follows the declared key order; numeric
fields may be JSON numbers; prompt v2; all-null rows dropped). Before the full loop, for each of
the 3 models the notebook runs its `img_only` compact config on `splits/smoke5.json` (5 spike40
docs picked by meta tags: 1 waybill, 1 multipage invoice, 3 single-page invoices; `--limit 5`) as
run_id `smoke_<config>_<sha7>` under `runs/smoke/`, then asserts from `trace.jsonl` and
`predictions.json` (`shipdoc.smoke.check_smoke`):

- (a) JSON-valid page rate == 1.0
- (b) no page with `n_output_tokens >= max_new_tokens`, and no unterminated raw output
- (c) every invoice has at least 1 emitted row; total emitted invoice rows within +-50% of gold
- (d) non-null `quantity` share among emitted rows >= 0.8
- (e) non-null `total_amount` on >= 2/3 of the invoices
- (f) no all-null rows after merge

Plus a non-blocking WARNING (never a failure, `shipdoc.smoke.warn_cpn_equals_po`): the count of
emitted rows whose customer_part_number equals the same row's purchase_order (identifier rule),
shown in the table as `WARN ... (non-blocking)` and stored per model under `warnings` in
`runs/smoke_status.json`.

A per-assertion PASS/FAIL table is printed per model and the result goes to
`runs/smoke_status.json` on Drive (resumable: models already passed for this commit are skipped,
a finished smoke run is re-checked rather than re-run). A model that fails (or errors, e.g. OOM) is
skipped: its configs are recorded as `skipped_smoke_fail` in `runs/spike40_status.json` and the
other models continue. If all three fail the notebook raises "SMOKE GATE FAILED FOR ALL MODELS"
before the full run.

**If the smoke fails, report back:** the printed per-assertion tables (or `runs/smoke_status.json`)
and, for the failing model, `runs/smoke/smoke_<config>_<sha7>/trace.jsonl` and `predictions.json`
(they hold the raw model output per page; they stay on Drive, do not paste document values into
chat). Do not edit thresholds to make a model pass.

The estimate uses `s_per_page = prefill_s + n_out / decode_tok_s` from `configs/spike_speed.json`.
Those values are trace-measured (OLS of `latency_s` on `n_output_tokens` per config over the
spike40 traces at 51cf560, see `reports/spike_diagnosis.md`); a source containing "placeholder"
makes the table say so. Compute units are shown only if `t4_cu_per_hour` is set there.

After the spike table the notebook runs `python -m scripts.paired_rank`: rank by OVERALL, paired
bootstrap (2000, seed 42) of the top two on the shared docs. If their individual 95% CIs overlap
(decision `run_dev100`), the top two run on `splits/dev100.json` (run_ids `dev100_<config>_<sha7>`,
status file `runs/dev100_status.json`, same resume mechanics) and are re-ranked; the final pick is
printed. Otherwise (`pick_top1`) dev100 is skipped. Fewer than 2 complete runs gives
`insufficient_runs` and no pick. The last line is
`DONE <run_group>_<sha7> decision=<decision> final_pick=<config> ab_decision=<keyed|compact>`.

### Keyed vs compact A/B (between the ranking and dev100)

GG-approved; motivated by the Step L root cause #2 (rotations among spn/cpn/po). The spike configs
are compact. For rank #1 the notebook runs the keyed twin (same name without `_compact`; json
output, full field names in declared order) on spike40 as run_id `ab_keyed_<keyed config>_<sha7>`
(same `run_stream` / `--resume` mechanics, own status file `runs/ab_status.json`), then
`python -m scripts.format_ab` and prints the table (OVERALL and row F1 with CIs, the paired
keyed - compact deltas, per-field row accuracy, rotations / clean swaps / cpn==PO, s/page) and the
decision with its reason; the JSON goes to `runs/ab_result.json`. Rule: choose KEYED if (row F1
keyed > compact AND the paired CI of delta row F1 excludes 0) OR (rotations keyed < rotations
compact AND OVERALL not worse), where "OVERALL not worse" = point delta OVERALL >= 0 OR the paired
CI of delta OVERALL includes 0; otherwise COMPACT on speed. dev100 policy: rank #1 uses the A/B
decision; rank #2 has no A/B, so it is compact unless the A/B chose keyed, then it runs keyed too
(the effect is format-level). A failed or OOM keyed run falls back to compact and records why in
`ab_status.json`.

Resume and re-run:

- Run outputs go to `MyDrive/shipdoc-extract/runs/<RUN_GROUP>_<config>_<sha7>/`
  (`predictions.json`, `trace.jsonl`, `metrics.json`, `progress.json`), checkpointed by the CLI's
  `--resume`, so a Colab disconnect loses at most the page in flight.
- After each config the notebook writes `runs/<RUN_GROUP>_status.json` (`done` / `failed`, exit
  code, `reason: "oom"` when detected, last output lines). Run all again after a disconnect:
  `done` configs are skipped, `failed` and partial ones resume.
- The last cell prints a table (OVERALL [CI], scanned-slice OVERALL, false-fill, JSON validity,
  s/page, peak VRAM) from every `metrics.json`, then `DONE <run_group>_<sha7>`. Cells that cannot
  be found in a `metrics.json` show `n/a`; the lookup paths are in the summary cell.

## 02_zeroshot500: zero-shot Qwen3.5-4B on all 500 train+dev docs

zero-shot over the 500 docs / 671 pages of `splits/zeroshot500.json` (400 train + 100 dev). The
output is (1) the out-of-fold baseline for gate G4 (zero-shot is unseen by construction) and (2) the
training data of the Phase 5 calibrator, so every trace page also carries per-field token logprobs
(`field_logprobs` and `token_logprobs`; schema in `src/shipdoc/trace.py`, method in
`src/shipdoc/logprobs.py`).

One-time inputs on Drive (`MyDrive/shipdoc-extract/` of your-drive-account@example.com): `data.zip` and
`assignment.zip` (the scorer). No OCR cache is needed. Colab secrets: `GH_TOKEN` (required),
`HF_TOKEN` (optional). **No W&B** (`USE_WANDB = False`; switching it on adds `--wandb` and needs the
`WANDB_API_KEY` secret and a Private `shipdoc-extract-debug` project; metrics only).

Each run: open the notebook from GitHub at the **PIN commit** (`chore(notebooks): pin 02_zeroshot500
to <sha7>`), Runtime -> T4 GPU, Run all. Cells in order:

1. Parameters (`PINNED_SHA`, filled by the pin commit; the placeholder `FILL_PINNED_SHA` makes the
   first cell raise), account check and Drive mount, secrets, clone at the pin
   (`HEAD == PINNED_SHA` asserted), unzip `data.zip` / `assignment.zip` to `/content`.
2. **Estimate, printed before anything runs**: T4 hours and compute units for smoke + full run in
   four length scenarios (gold mean, observed spike40 mean, p99, every page at `max_new_tokens`), at
   both CU rates (1.19 and 1.58 per hour, third-party figures, see `configs/spike_speed.json`), with
   the 120 s model-load ESTIMATE per load. There is no confirmation prompt: read it, interrupt if too
   high.
3. `uv sync --frozen --group vlm`, GPU / torch / xgrammar probe (asserts an `sm_75` kernel).
4. **Smoke gate (mandatory)**: the 5 docs of `splits/smoke5.json` (`--limit 5 --logprobs`), then the
   assertions of `shipdoc.smoke` (a-f as in 01, plus **g**: every emitted header / row field of every
   valid page has finite `field_logprobs` with >= 1 token) and the non-blocking `cpn==PO` warning. A
   failure raises `SMOKE GATE FAILED ... NOT started` and the full run cannot be executed (its cell
   re-checks the gate). The result is saved in `runs/zeroshot500_smoke_status.json`; a passed smoke of
   the same run id is not repeated. Thresholds are never edited to pass.
5. **Full run**: one `python -m shipdoc spike --split train+dev --logprobs --resume` subprocess over
   all 500 docs, run_id `zeroshot500_qwen35_4b_img_only_keyed_<sha7>`, output folder
   `MyDrive/shipdoc-extract/runs/<run_id>/`. Per document the CLI appends one fsync'd line to

   the end. A `[progress]` line is printed (checked every 60 s) whenever documents have finished; `sessions.json` logs the
   wall-clock of every Run all.
6. **Banner**: docs / pages done, OVERALL with CI on the 500 docs, train and dev numbers, JSON-valid
   and false-fill rates, wall-clock, the Drive folder, and the files to download:
   `predictions.json`, `trace.jsonl`, `metrics.json`, `progress.json` (plus `sessions.json`). Last
   line: `DONE <run_id> docs=500 pages=671 complete=True`.

Disconnect / quota: Run all again. `/content` is empty after a disconnect, so the setup, estimate and
install cells repeat (a few minutes of T4), the smoke is skipped, and the full run resumes after the
last document in `trace.jsonl` (`--resume`); nothing finished is redone and `predictions.json` ends
byte-identical to an uninterrupted run (tested with a kill mid-document, a torn last line and a
missing newline, `tests/test_zeroshot500.py`). The document in flight when the session died is
redone from page 1. A resume is only valid on the same pin (the sha7 is in the run id); a re-pin is a
new run id.

CUDA OOM: the cell raises "CUDA out of memory" with the last doc finished; everything before it is
on Drive and Run all resumes. If it stops again at the same document, report that doc id (it is in
`progress.json` as `last_doc`, the failing one is the next in `splits/zeroshot500.json`); do not
change `max_pixels` or `max_new_tokens` to get past it, that would change the baseline.

### 02 parameters: batch size, shards, merge

The parameters cell of 02 also holds four knobs that change how the full run is executed, not what
it computes. Cell order is: setup, shard plan, estimate, install, smoke gate, **bench**, full run,
**merge**, banner.

- `BATCH_SIZE` (`None` | int, default `None`): pages per generate call. `None` = the bench decides.
  An int is manual: the bench is skipped, a banner says nothing verified that this size gives the
  same outputs as batch 1, and the size is recorded as `manual` in `manifest.json`.
- `BENCH_DOCS` (`splits/bench12.json`): the 12 dev pages of the bench (`python -m shipdoc bench`,
  `src/shipdoc/bench.py`), run after the smoke gate at batch 1, 2, 4, 8 (real pipeline, logprobs
  on). Rule (verbatim in `bench_result.json`): the largest size with 100% byte-identical outputs vs
  batch 1 and peak VRAM <= 14.5 GiB; if none above 1 qualifies, the largest with >= 99.5% field
  agreement and an identical scorer result, flagged as a DEVIATION in the manifest and the banner;
  else batch 1. Throughput is reported, never used to decide. The result is saved on Drive
  (`runs/bench_<config>_<sha7>/bench_result.json`) and reused by a later tab or a resumed session
  only while code SHA, config hash and model revision are the same (`--reuse`).
- `SHARD` (`"i/K"`, default `"0/1"`): this tab runs document-level shard `i` of `K`
  (`src/shipdoc/shard.py`: documents by pages descending, each to the shard with the fewest pages
  so far, so the page totals differ by at most one document). A shard writes its own folder
  `<run_id>_shard<i>of<K>`; `K = 2` means two Colab tabs started on the same pin, with the same
  batch size (the bench is deterministic given the same code and GPU model, a later tab reuses the
  finished result, or set `BATCH_SIZE` to the same int in both). The CU of the tabs add up.
- `MODE` (`"run"` | `"merge"`, default `"run"`): `"merge"` (with `SHARD = "0/K"`, `K >= 2`) combines
  the K shard folders into `<run_id>` on the CPU (no torch install). `python -m shipdoc
  merge-shards` refuses, writing nothing, unless every shard is complete and the shards agree on
  code SHA, config hash, model revision, seed, batch size, split, arm, output format, logprobs and
  the doc-list hash, no document appears twice, the documents are exactly the doc list and the
  counts are the expected 500 / 671. The merged `trace.jsonl`, `predictions.json` and
  `metrics.json` equal an unsharded run's (`tests/test_shards.py`).

The estimate cell also prints a T4-hour / CU table per batch size (1, 2, 4, 8 at assumed scaling
efficiencies 100 / 75 / 50%) for one and two tabs, labelled ESTIMATE: the batching gain is an
assumption until the bench measures it.

Batch size contract: greedy outputs are only comparable at the same batch size. The bench result of
the dev/zero-shot run must also size the TEST submission (notebook 04 enforces this with
`shipdoc.runmeta.require_same_batch_size`).

Pin commit (done by GG after the code commit is pushed; the code commit is the one just before it).
The single placeholder is `ZS_PINNED_SHA = "FILL_PINNED_SHA"` in `scripts/colab_build_notebook.py`:

```
sed -i 's/^ZS_PINNED_SHA = "FILL_PINNED_SHA"/ZS_PINNED_SHA = "<40-hex code commit>"/' scripts/colab_build_notebook.py
uv run python scripts/colab_build_notebook.py
uv run pytest -q tests/test_notebook_zeroshot.py tests/test_notebook_spike.py

```

Unverified on a GPU (no GPU was available when this was written): the logprob processors inside
`HfBackend.generate`, their effect on decode speed, and the T4-hour / CU estimate. The smoke gate is

## 03_finetune: LoRA fine-tune of Qwen3.5-4B (smoke stage first)

`notebooks/03_finetune.ipynb` is generated by `scripts/colab_build_finetune.py` (outputs cleared;
edit the script, not the JSON). The logic is `python -m shipdoc.trainset` (training plan) and
`python -m shipdoc.train` (loop); every hyper-parameter is in `configs/finetune_qwen35_4b.yaml`
(seed 42). **Pinned** (corrected 2026-10-03; this paragraph used to say it was not): the notebook
is pinned to code commit `42b812b` by the pin commit `6c2fa30`, and fold 0 was trained from it
(`ft_fold0_42b812b_bf16`). A placeholder `FILL_PINNED_SHA` makes the first cell raise, which is how
the unpinned native sibling `03n_finetune_native` ships. Same Drive inputs as 01_spike (`data.zip`, `assignment.zip`, `ocr_cache.zip` in
`MyDrive/shipdoc-extract/`; the OCR cache is needed for the row-to-page plan and the occlusion
candidates) and the same Colab secrets (`GH_TOKEN` required; `WANDB_API_KEY` only if `USE_WANDB`).

**Run the smoke first.** The parameter `STAGE` in the parameters cell is one of `smoke`, `fold0`,
`fold1`, `fold2`, `final` and defaults to `smoke`. Runtime -> Run all with the default runs
everything up to and including the 20-step smoke and then prints the completion banner; nothing
else is trained. Recommended runtime: **L4** (bf16, no scaler); a T4 works too (fp16 +
`GradScaler`, fp32 LoRA weights) and is chosen automatically from the GPU.

Cells, in order: parameters -> Drive + secrets -> clone at the pin -> unzip -> **estimate** (GPU
hours and CU per stage for the detected GPU, from `scripts/finetune_estimate.py`; printed before
anything runs, no confirmation prompt, interrupt if too high; UNVERIFIED model) -> install
(`uv sync --frozen --group vlm --group train`; `peft==0.21.2` is in the locked `train` group)
and GPU probe -> prepare (CPU, cached as
`runs/prepared_all.json` + `runs/audit.jsonl`: page of every gold row, header-only documents,
occlusion candidates) -> **smoke** (always; a failure raises and nothing after it runs) -> the
chosen stage (skipped for `smoke`) -> completion banner (loss-curve summary, held-out loss for
information, s/step, peak VRAM, wall-clock, the exact files to download).

Smoke criteria (`shipdoc.train.smoke_checks`, abort before any full run): the mean loss of the last
5 of 20 optimizer steps is below 0.95 x the first 5; peak VRAM under the budget in the config (20
GiB bf16, 13.5 GiB fp16); 200 LoRA modules and 30,474,240 trainable parameters; no NaN / inf; a
checkpoint written to Drive reloads bit-identical. It also preflights the longest-target page.

Outputs go to `MyDrive/shipdoc-extract/runs/<run_id>/` with `run_id = ft_<stage>_<sha7>_<precision>`
(smoke: `ft_smoke_<sha7>_<precision>`): `ckpt/step_NNNNNN/` (adapter + optimizer + scheduler +
scaler + RNG + step + sampler position, every 10 steps, the newest two kept), `metrics.jsonl`,
`sessions.json`, `smoke_status.json` / `train_status.json`, and for a finished stage
`final/adapter.pt` and `final/peft/`. **Resume**: if the session dies, open the notebook and Run
all again; the smoke is skipped (it passed) and the stage continues from the newest checkpoint.
The resume is exact (same weights, optimizer moments, schedule and data order as an uninterrupted
run) and refuses a checkpoint written under a different config or precision.

There is no early stopping on held-out loss (departure from spec Phase 4.3, reports/finetune_plan.md
"Leakage note"): the fixed 2-epoch schedule is used and the held-out loss is logged for information
only (24 fixed held-out pages, every 10 steps and at each epoch end; no code path reads it to stop
or to choose a checkpoint, and it is RNG-neutral). Report back after the smoke: the printed banner
and `smoke_status.json` (no document values in either); do not edit the thresholds to make it pass.

**Stage order: fold0 first, the rest only after its OOF inference.** After the smoke passes:

1. `STAGE = "fold0"` (nothing else changed; `PINNED_SHA` is the pin commit) and Run all. The smoke
   of this pin is run or skipped first, then fold 0 trains (441 pages x 2 epochs = 112 optimizer
   steps of 8 pages) and writes `<run>/final/` = `adapter.pt`, `manifest.json` (signature, steps,
   base revision, adapter sha256) and `peft/`. The fold0 banner repeats the next step.
2. Run the OOF inference of fold 0's held-out pages (230) on a T4 with that adapter and compare it
   with zero-shot on the held-out suppliers.
3. **`fold1`, `fold2` and `final` run ONLY if fold 0 shows no regression versus zero-shot on its
   held-out suppliers.** The notebook has no code gate for this; it prints a reminder in the fold0
   banner and before fold1 / fold2 / final.

`USE_WANDB` defaults to `True` for `fold0`, `fold1`, `fold2` and `final` (and `False` for the
smoke): scalar curves (train loss, grad norm, lr, held-out loss) go to the private project
`shipdoc-extract-debug`, never images or values. Without a `WANDB_API_KEY` Colab secret, or if W&B
is unreachable, the run prints one line and continues without it; training never fails on W&B.

`metrics.jsonl` holds exactly one line per optimizer step, steps 1..n once each. A session that
dies before the first checkpoint restarts at step 0 and the file is reset (the dead session's lines
go to `metrics_discarded.jsonl`); the first L4 smoke printed "29 / 20" before this was fixed
(`reports/finetune_plan.md`, "Smoke measurement"). The banner reads the file through
`shipdoc.metricslog` and warns if an old-style file still carries duplicates.

## 04_predict_test: safety submission v0 on the 200 test documents

`notebooks/04_predict_test.ipynb` (built by `scripts/colab_build_predict.py`; edit the script, not
the JSON) predicts all 200 test documents / 280 page images with the production config and writes a
validated submission folder. Logic is in `python -m shipdoc predict <stage>` (`src/shipdoc/predict.py`).

**Config** (unchanged from the dev100 pick): Qwen3.5-4B, image only, KEYED output format, prompt v2,
greedy decoding, seed 42, fp16 on a T4 (`configs/spike_qwen35_4b_img_only.yaml`), logprobs on (as in
the bench). **Phase 3 post-processing = the repo default** (`reports/ablations.md` G3):
ON provenance-aware merge (page-1 identity, last-page totals), repeated header-row filter, drop
all-null rows, dates to ISO, number normalisation, code normalisation (currency, airport);
OFF OCR labelled-total pointer (no OCR at inference), per-layout-cluster day/month order (no
clusters at inference); the ISO 4217 / IATA / AWB validators give flags only and are not run here.
`manifest.json` records the exact switches (read from the code defaults; a test replays the traces
through them and reproduces every prediction). **No OCR stage**: Paddle is not installed (the
notebook asserts it is absent) and never run.

**Test data policy.** Test images are read only through the inference loaders; there are no test
labels (the notebook asserts `data/test/labels` does not exist). Document ids come from the test
image file names. Nothing prints or logs an extracted value: the validation report, the determinism
report and the banner carry counts, ids and key paths only. Test predictions never enter git:
`submissions/` is gitignored, the notebook writes only to Drive, and `shipdoc predict assemble`
refuses an output folder inside the repo tree (except the ignored `submissions/`).

One-time inputs on Drive (`MyDrive/shipdoc-extract/` of your-drive-account@example.com): `data.zip`
(must contain `data/test/images`) and `assignment.zip` (schema, sample submission). No OCR cache.
Colab secrets: `GH_TOKEN` (required), `HF_TOKEN` (optional). No W&B.

Parameters: `PINNED_SHA` (a stand-in until GG re-pins), `BATCH_SIZE`, `SHARD`, `MODE` (as in 02,
see "02 parameters"), and `DEV_RUN_DIR`: the dev run folder under `runs/` (default the 02 zero-shot
folder at pin b10d810) whose manifest holds the batch size and the bench result the test run must
match. `None`, or a folder without a manifest, is allowed but loud: the bench runs as is and the

### Review flags and the frozen calibrator

`review_flags.json` (`python -m shipdoc.flags`): top-level metadata (`arm`, `calibrator` with its
sha256, `thresholds` with the field tau per type, the document tau, the targets, the nested
estimates and whether the nested precision reached the target, `inputs` with the sha256 of the
predictions and the trace, `summary`) and `docs`: per document id `p_fully_correct`, `auto_accept`,
`header` (field name -> `emitted`, `p_correct`, `flag` = `accept` | `review`) and `rows` (list of
`row_idx` + `fields`, same shape). A null field has `emitted: false, p_correct: null, flag: null`:
the calibrators score emitted fields only (calibration v2 has no null policy). A field is accepted
iff `p_correct >= tau(type)`; `tau = null` (the target is never reached on the pooled OOF
predictions) sends every field of that type to review. The document is auto-accepted iff
`p_fully_correct >= doc tau`. `check-flags` verifies: exactly the 200 ids, every string value under
`docs` is `accept` / `review` and no prediction value (4+ characters) occurs anywhere in the file,
thresholds and nested estimates recorded, the calibrator sha256 equals the file's, the file belongs
to these predictions (sha256 of `test_predictions.json` and `trace.jsonl`).

and traces with different ids or not 200 docs; a manifest whose model (LoRA or not) does not match

`scripts/freeze_calibrator.py` freezes the artifact (`meta/calibrator_<arm>.json`, one JSON line,
small): `--arm zs --run-dir <02 run> --calibration-dir <calibrate_v2 output>` (exists) and

tau:

* Structure and kind (pooled / per_type, LR / GBM): copied from the calibration run (not
  re-selected). The field models are fitted on ALL emitted rows of the 500 train + dev documents
  (the production calibrator is fit on everything). A training row's layout novelty is computed
  against the OTHER supplier folds (what the cross-fit does for its fitting rows); at inference
  against the cluster centres of all 500 signatures, stored in the artifact.
* tau: per field type (header + four row fields) and target 95 / 98 / 99%, `confidence.select_tau`
  on ALL POOLED out-of-fold predictions of that type; for documents at 95 / 98% on the pooled OOF
  document probabilities (recomputed by the supplier-fold document cross-fit and checked against
  `oof_docs_v2.csv` for ZS). The nested protocol (tau of fold k from the other folds, applied to
  fold k) is the honest EVALUATION of such a rule; its three per-fold taus are not a production
  threshold, so the production tau is the same rule on all OOF evidence at once. The nested
  estimates (precision, coverage, review rate, error recall, document-bootstrap CIs) and a flag
  `nested_target_met` per type are stored next to the taus as the expected performance; the pooled
  in-sample precision / coverage at tau is stored too and is optimistic. The final model's
  probabilities differ a little from the cross-fitted ones tau was chosen on (more data, in-sample
  fit), and the document model, fitted on OOF field probabilities, sees the final model's sharper
  ones at inference (stacking caveat): read the nested numbers, not the in-sample ones.
* Parity: the artifact records the feature column names and a digest of the design matrix that the
  feature code builds for a fixed synthetic document (`flags.parity_probe`); the flags stage builds

* Portability: LR models are plain coefficients, imputer fills and scaler (no sklearn at
